# Атрибуты качества ПО (ISO/IEC 25010)

> Справочный материал курса «Жизненный цикл разработки ПО».
> Описывает модель качества SQuaRE и её применение при формулировании нефункциональных требований.

## 1. Что такое атрибуты качества

**Атрибуты качества ПО** (Quality Attributes) — это характеристики системы, которые описывают не то, **что** программа делает, а **как** она это делает.

- Функциональные требования отвечают на вопрос: *«Что делает система?»*
- Нефункциональные требования отвечают на вопрос: *«Насколько хорошо система выполняет функции?»*

**Стандарт:** ISO/IEC 25010:2011 *Systems and software Quality Requirements and Evaluation (SQuaRE)*

---

## 2. Модель качества ISO 25010

Стандарт определяет **8 основных характеристик**, каждая из которых разбивается на подхарактеристики:

```text
┌─────────────────────────────────────────────────────────────┐
│                 Качество продукта (ISO 25010)               │
├─────────────────────────────────────────────────────────────┤
│  1. Functional Suitability    2. Performance Efficiency     │
│  3. Compatibility             4. Usability                  │
│  5. Reliability               6. Security                   │
│  7. Maintainability           8. Portability                │
└─────────────────────────────────────────────────────────────┘
```

---

## 3. Детальный разбор характеристик

### 3.1 Functional Suitability (Функциональная пригодность)

Способность продукта предоставлять функции, соответствующие заявленным потребностям.

| Подхарактеристика | Смысл |
|-------------------|-------|
| **Functional completeness** | Полнота покрытия заявленных задач |
| **Functional correctness** | Корректность результатов |
| **Functional appropriateness** | Уместность функций для пользователя |

**Пример требования:**
> *«Система должна корректно рассчитывать итоговую сумму заказа с учётом налогов, скидок и стоимости доставки для всех поддерживаемых валют (BYN, EUR, USD).»*

---

### 3.2 Performance Efficiency (Производительность)

Отношение производительности к используемым ресурсам в заданных условиях.

| Подхарактеристика | Смысл | Метрика |
|-------------------|-------|---------|
| **Time behaviour** | Время отклика, обработки | мс, сек |
| **Resource utilisation** | Использование CPU, памяти, диска | %, MB, GB |
| **Capacity** | Максимальные нагрузки | RPS, concurrent users |

**Пример требования:**
> *«Время отклика API `/api/orders` не должно превышать 200 мс в 95-м процентиле при нагрузке до 1000 RPS.»*

---

### 3.3 Compatibility (Совместимость)

Способность продукта взаимодействовать с другими системами и сосуществовать с ними.

| Подхарактеристика | Смысл |
|-------------------|-------|
| **Co-existence** | Совместная работа с другими продуктами без конфликтов |
| **Interoperability** | Обмен данными с другими системами |

**Пример требования:**
> *«Система должна поддерживать обмен данными с ERP-системой заказчика через REST API по протоколу OpenAPI 3.0.»*

---

### 3.4 Usability (Удобство использования)

Эффективность, производительность и удовлетворённость пользователя.

| Подхарактеристика | Смысл |
|-------------------|-------|
| **Appropriateness recognisability** | Понятность назначения продукта |
| **Learnability** | Обучаемость |
| **Operability** | Простота эксплуатации |
| **User error protection** | Защита от ошибок пользователя |
| **User interface aesthetics** | Эстетика интерфейса |
| **Accessibility** | Доступность для людей с ограниченными возможностями |

**Пример требования:**
> *«Интерфейс должен соответствовать WCAG 2.1 уровня AA. 95% новых пользователей должны выполнить основной сценарий без обращения к документации.»*

---

### 3.5 Reliability (Надёжность)

Способность выполнять функции в заданных условиях в течение заданного периода.

| Подхарактеристика | Смысл | Метрика |
|-------------------|-------|---------|
| **Maturity** | Зрелость (отсутствие дефектов) | Defects/KLOC |
| **Availability** | Готовность к работе | % uptime |
| **Fault tolerance** | Устойчивость к сбоям | — |
| **Recoverability** | Восстанавливаемость | MTTR |

**Пример требования:**
> *«Система должна обеспечивать доступность 99,95% (допускается до 4,4 часа простоя в год). Восстановление после сбоя — не более 5 минут (MTTR).»*

---

### 3.6 Security (Безопасность)

Защита информации и обеспечение доверия.

| Подхарактеристика | Смысл |
|-------------------|-------|
| **Confidentiality** | Конфиденциальность |
| **Integrity** | Целостность данных |
| **Non-repudiation** | Невозможность отказа от действий |
| **Authenticity** | Подлинность субъектов и данных |
| **Accountability** | Подотчётность действий |

**Пример требования:**
> *«Все персональные данные должны шифроваться при передаче (TLS 1.3) и хранении (AES-256). Доступ к данным должен журналироваться с невозможностью отказа от действий.»*

---

### 3.7 Maintainability (Сопровождаемость)

Простота модификации продукта.

| Подхарактеристика | Смысл |
|-------------------|-------|
| **Modularity** | Модульность |
| **Reusability** | Повторное использование |
| **Analysability** | Анализируемость |
| **Modifiability** | Модифицируемость |
| **Testability** | Тестируемость |

**Пример требования:**
> *«Цикломатическая сложность функций не должна превышать 15. Покрытие unit-тестами — не менее 80%.»*

---

### 3.8 Portability (Переносимость)

Способность переноситься из одной среды в другую.

| Подхарактеристика | Смысл |
|-------------------|-------|
| **Adaptability** | Адаптируемость к разным средам |
| **Installability** | Простота установки |
| **Replaceability** | Заменяемость аналогичными продуктами |

**Пример требования:**
> *«Приложение должно работать в контейнерах Docker на Linux, Windows и macOS, поддерживая горизонтальное масштабирование в Kubernetes.»*

---

## 4. Компромиссы между атрибутами

Атрибуты качества часто **конфликтуют** друг с другом. Проектирование — это поиск баланса.

| Конфликт | Суть |
|----------|------|
| **Security ↔ Performance** | Шифрование замедляет систему |
| **Usability ↔ Security** | Многофакторная аутентификация усложняет UX |
| **Performance ↔ Maintainability** | Оптимизации усложняют код |
| **Reliability ↔ Cost** | Избыточность увеличивает стоимость |
| **Portability ↔ Performance** | Абстракции для портируемости замедляют систему |

**Задача архитектора** — осознанно принимать компромиссы и фиксировать их в ADR.

## 5. Как формулировать атрибуты качества

### 5.1 Правило SMART

Каждое нефункциональное требование должно быть:
- **Specific** — конкретным
- **Measurable** — измеримым
- **Achievable** — достижимым
- **Relevant** — значимым
- **Time-bound** — с указанием условий/времени

### 5.2 Шаблон формулировки

```text
<СИСТЕМА> должна <АТРИБУТ> <МЕТРИКА> при <УСЛОВИЯХ>.
```

### 5.3 Плохие и хорошие примеры

| Плохо ❌ | Хорошо ✅ |
|----------|----------|
| *«Система должна быть быстрой»* | *«95% запросов должны обрабатываться менее чем за 200 мс при нагрузке 1000 RPS»* |
| *«Интерфейс должен быть удобным»* | *«Новый пользователь должен выполнить целевое действие за 3 клика без подсказок»* |
| *«Система должна быть надёжной»* | *«Доступность системы — 99,9% с MTTR ≤ 15 минут»* |
| *«Система должна быть безопасной»* | *«Передача данных — TLS 1.3, хранение паролей — bcrypt с коэффициентом 12»* |

## 6. Атрибуты качества в SRS

В шаблонах репозитория атрибуты качества располагаются в разделе **3.3 Quality of Service**:

| Подраздел SRS | Соответствующая характеристика ISO 25010 |
|---------------|-----------------------------------------|
| 3.3.1 Performance | Performance Efficiency |
| 3.3.2 Security | Security |
| 3.3.3 Reliability | Reliability (maturity, fault tolerance) |
| 3.3.4 Availability | Reliability (availability) |
| 3.3.5 Observability | Maintainability (analysability) |

Дополнительно:
- **3.4 Compliance** — соответствие стандартам (часть Compatibility)
- **3.5 Design and Implementation** — Maintainability, Portability
- **3.1 User Interfaces** — Usability

---

## 7. Верификация атрибутов качества

| Атрибут | Методы проверки |
|---------|----------------|
| **Performance** | Нагрузочное тестирование (JMeter, Gatling) |
| **Reliability** | Chaos Engineering, отказоустойчивые тесты |
| **Security** | Пентесты, SAST, DAST, аудит кода |
| **Usability** | UX-тестирования, A/B тесты |
| **Maintainability** | Статический анализ (SonarQube), code review |
| **Portability** | Кросс-платформенное тестирование |
| **Compatibility** | Интеграционное тестирование |

---

## 8. Инструменты измерения

| Атрибут | Инструменты |
|---------|-------------|
| **Производительность** | JMeter, Gatling, k6, Prometheus |
| **Наблюдаемость** | Prometheus, Grafana, Jaeger, ELK |
| **Надёжность** | Chaos Monkey, Gremlin |
| **Безопасность** | OWASP ZAP, Snyk, SonarQube |
| **Сопровождаемость** | SonarQube, CodeClimate |
| **Удобство** | Hotjar, UserTesting |

## 9. Пример: полный набор QoS для веб-сервиса

```markdown
## 3.3 Quality of Service

### 3.3.1 Performance
- REQ-PERF-001: API response time ≤ 200ms (p95) at 1000 RPS
- REQ-PERF-002: Page load time ≤ 2s on 3G connection

### 3.3.2 Security
- REQ-SEC-001: All traffic over TLS 1.3
- REQ-SEC-002: Passwords hashed with bcrypt (cost ≥ 12)
- REQ-SEC-003: Session timeout after 30 min of inactivity

### 3.3.3 Reliability
- REQ-REL-001: Availability ≥ 99.95% (annual)
- REQ-REL-002: MTTR ≤ 5 minutes for P1 incidents

### 3.3.4 Observability
- REQ-OBS-001: All API requests traced with unique IDs
- REQ-OBS-002: Metrics retention ≥ 90 days
```
