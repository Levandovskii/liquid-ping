# Терминология: Что не переводится

> В международной инженерной практике ряд терминов устоялся и не переводится на национальные языки.
> Настоящий справочник фиксирует такие термины для репозитория `sw-doc-templates` и связанных проектов.

## Принципы терминологии

1. **Не переводим** термины, которые являются международными идентификаторами артефактов (SRS, SDD, ADR).
2. **Переводим** описательные понятия (требование, представление, точка зрения).
3. **Сохраняем аббревиатуры** для краткости и однозначности ссылок.

---

## Основные непереводимые термины

| Термин | Расшифровка | Пояснение |
|--------|-------------|-----------|
| **SRS** | Software Requirements Specification | Спецификация требований к ПО. Артефакт, описывающий ЧТО система должна делать. |
| **SDD** | Software Design Description | Описание дизайна ПО. Артефакт, описывающий КАК система построена. |
| **ADR** | Architecture Decision Record | Запись архитектурного решения. |
| **MADR** | Markdown Architecture Decision Records | Формат ADR на Markdown. |
| **SDS** | Software Design Specification | *Устаревший* термин (IEEE 1016-1998), заменён на SDD. |
| **BRD** | Business Requirements Document | Документ бизнес-требований. |
| **PRD** | Product Requirements Document | Документ продуктовых требований. |
| **DDS** | Design Document Specification | Альтернативное название SDD. |
| **TP** | Test Plan | План тестирования. |

## Технические термины

| Термин | Пояснение |
|--------|-----------|
| **Viewpoint** | Точка зрения — конвенция о построении View (ISO 42010). Переводится как «точка зрения» при раскрытии. |
| **View** | Представление — экземпляр Viewpoint. Переводится как «представление». |
| **Concern** | Заинтересованность стейкхолдера. |
| **Stakeholder** | Стейкхолдер (заинтересованная сторона). Часто не переводится. |
| **Traceability** | Трассируемость. Переводится. |
| **Baseline** | Базовая линия (требований). Переводится. |
| **Change Request** | Запрос на изменение. Переводится как «запрос на изменение», но в технической коммуникации часто оставляют. |
| **CCB** | Change Control Board — коллегиальный орган управления изменениями. |
| **Scope Creep** | Неконтролируемое расширение границ проекта. |

## Стандарты и спецификации

Названия стандартов **не переводятся**:
- ISO/IEC/IEEE 29148:2018
- IEEE 1016-2009
- ISO/IEC/IEEE 42010:2011
- ISO/IEC 25010:2011
- IEC 62304
- DO-178C

При ссылках на стандарты используется оригинальное обозначение с годом.

---

## Правила оформления в документах

1. **Первое упоминание** — с расшифровкой: «Software Requirements Specification (SRS)».
2. **Далее** — только аббревиатура: «SRS содержит…».
3. **Множественное число** — добавлением `s`: SRSs, ADRs, Views.
4. **Прилагательное** — через дефис: SRS-документ, ADR-запись (в русском тексте).

---

## Примеры использования

✅ **Правильно:**
- «Команда подготовила SRS в соответствии с ISO/IEC/IEEE 29148.»
- «Архитектор ведёт ADR для каждого значимого решения.»
- «Матрица трассируемости связывает требования SRS с компонентами SDD.»

❌ **Неправильно:**
- «Команда подготовила СПТПО.» (искусственная русская аббревиатура)
- «Запись архитектурного решения в формате МАДР.» (русская транслитерация MADR)
- «Описание Дизайна Программного Обеспечения.» (калька, не используется)

---

## Резюме

Термины **SRS, SDD, ADR, MADR, Viewpoint, View** и другие международные обозначения являются частью профессионального языка инженера ПО. Их сохранение в оригинальном виде:
- Обеспечивает однозначность ссылок между документами
- Позволяет работать с международными командами
- Облегчает поиск информации в сети и стандартах
- Подчёркивает профессиональную зрелость документации
