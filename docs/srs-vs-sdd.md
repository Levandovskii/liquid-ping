# SRS vs SDD: Различия и взаимосвязи

> Справочный материал курса «Жизненный цикл разработки ПО».
> Объясняет разницу между спецификацией требований (SRS) и описанием дизайна (SDD), их роли в жизненном цикле и принципы трассируемости.

## 1. Сравнительная таблица

| Аспект | SRS | SDD |
|--------|-----|-----|
| **Расшифровка** | Software Requirements Specification | Software Design Description |
| **Вопрос** | **ЧТО** должна делать система? | **КАК** система будет построена? |
| **Уровень абстракции** | Чёрный ящик (внешнее поведение) | Белый ящик (внутренняя структура) |
| **Аудитория** | Заказчик, бизнес-аналитик, QA, продукт | Архитектор, разработчик, DevOps, SRE |
| **Автор** | Системный / бизнес-аналитик | Архитектор / Tech Lead |
| **Стандарты** | IEEE 830, ISO/IEC/IEEE 29148 | IEEE 1016, ISO/IEC/IEEE 42010 |
| **Язык описания** | Естественный язык, User Stories, Use Cases | UML, C4, диаграммы, псевдокод |
| **Стабильность** | Относительно стабилен (базовая линия) | Эволюционирует вместе с системой |
| **Тестирование** | Источник тестовых сценариев | Источник unit/integration-тестов |

---

## 2. ⚠️ Важное замечание о термине SDS

Исторически использовался термин **SDS** (*Software Design Specification*, IEEE 1016-1998).
Современный стандарт **IEEE 1016-2009** использует термин **SDD** (*Software Design Description*).

В русскоязычной практике и legacy-проектах встречаются оба термина. В международной инженерной литературе и современных шаблонах **SDD** является актуальным.

В русскоязычных государственных проектах (ГОСТ 34.602) используется термин **ТЗ** (Техническое задание), которое по смыслу ближе к SRS.

## 3. Метафора: Здание

Представьте, что вы строите здание.

| Артефакт | Аналог |
|----------|--------|
| **Vision & Scope** | Концепция: «Нужен бизнес-центр класса A на 30 этажей» |
| **SRS** | Техническое задание заказчику: «12 переговорных, паркинг на 500 мест, время доставки лифта до 30 сек» |
| **SDD** | Проект архитектора: «Несущий каркас из железобетона, фундамент свайный, лифты KONE, система вентиляции по такой-то схеме» |
| **ADR** | Протокол решения: «Выбрали железобетон вместо металлокаркаса, потому что…» |
| **Код** | Собственно построенное здание |

## 4. Жизненный цикл артефактов

```text
Vision & Scope
│
▼
SRS ─────────────────────────┐
│                            │
▼                            ▼
SDD ──────────────────────▶ ADR
│                            │
▼                            │
Код                          │
│                            │
▼                            │
Тесты ◀──────────────────────┘
```

### Последовательность создания

1. **Vision & Scope** — создаётся первым, задаёт «образ и границы» проекта.
2. **SRS** — фиксирует требования. Стабильная базовая линия.
3. **SDD** — строится на основе SRS. Эволюционирует.
4. **ADR** — ведётся параллельно, фиксирует значимые решения.

### Кто использует и когда

| Этап ЖЦ | SRS | SDD | ADR |
|---------|-----|-----|-----|
| Анализ | Пишется | Не используется | Возможно |
| Проектирование | Ссылка | Пишется | Пишется |
| Разработка | Редко | Основной документ | Ссылка |
| Тестирование | Источник тест-кейсов | Источник unit-тестов | Ссылка |
| Эксплуатация | Для аудита | Для поддержки | Для понимания истории |

## 5. Содержимое: что в чём?

### SRS содержит:
- Функциональные требования (что делает система)
- Нефункциональные требования (как хорошо)
- Внешние интерфейсы (UI, API, hardware)
- Пользователей и их характеристики
- Допущения и ограничения
- Критерии приёмки

### SDD содержит:
- Архитектурные представления (Viewpoints & Views)
- Компоненты, модули, классы
- Интерфейсы между компонентами
- Диаграммы (UML, C4, DFD)
- Обоснование архитектурных выборов
- Ссылки на реализованные требования SRS

### ADR содержит:
- Контекст проблемы
- Рассмотренные альтернативы
- Выбранное решение
- Обоснование выбора
- Последствия решения

## 6. Трассируемость: как они связаны

Каждое требование в SRS имеет **уникальный идентификатор** (например, `REQ-FUNC-001`). Этот ID используется:

| Откуда | Куда | Связь | Пример |
|--------|------|-------|--------|
| Vision | SRS | `derives from` | Бизнес-цель → требование |
| SRS | SDD | `satisfies` | Требование → компонент дизайна |
| SDD | SRS | `implements` | Компонент → требование |
| SRS | Тест | `verifies` | Требование → тест-кейс |
| ADR | SRS + SDD | `addresses` | Решение → требование + дизайн |

**Пример полной цепочки:**

```text
Бизнес-цель BR-01 (Vision)
│ derives from
▼
Требование REQ-FUNC-042 (SRS)
│ satisfies
▼
Компонент AuthService (SDD)
│ implements
▼
Тест TC-AUTH-001 (Test Plan)
│ verifies
▼
ADR-007: Использовать JWT вместо сессионных токенов
```

## 7. Когда что использовать

| Ситуация | Что нужно |
|----------|-----------|
| Согласовать с заказчиком, что делаем | **SRS** |
| Объяснить команде, как строим | **SDD** |
| Обосновать выбор технологии | **ADR** |
| Проверить, что всё реализовано | Матрица трассируемости SRS ↔ SDD |
| Найти, что сломается при изменении | Матрица зависимостей SDD |
| Восстановить историю решения | **ADR** |

## 8. Антипаттерны

| Ошибка | Последствия | Как правильно |
|--------|-------------|---------------|
| Писать SDD вместо SRS | Заказчик не понимает, что получит | SRS — «что», SDD — «как» |
| Не вести ADR | Через год никто не помнит, почему выбран PostgreSQL | Вести ADR для всех значимых решений |
| Отсутствие трассируемости | Нельзя оценить влияние изменений | Использовать ID требований |
| Дублировать текст между SRS и SDD | Рассинхронизация при изменениях | SDD ссылается на SRS по ID |
| Писать SRS после написания кода | Документация не соответствует реальности | SRS пишется **до** или **параллельно** с разработкой |

## 9. Эволюция в Agile

В Agile-методологиях классические SRS/SDD трансформируются, но их суть сохраняется:

| Классика | Agile-эквивалент |
|----------|------------------|
| SRS (монолит) | Product Backlog + User Stories + Acceptance Criteria |
| SDD (монолит) | ADR + README + диаграммы в коде (C4, Mermaid) |
| Базовая линия | Sprint Goal / Release Scope |
| Change Request | Уточнение на Sprint Planning |
| Матрица трассируемости | Связи в Jira + Definition of Done |

**Принцип остаётся:** «что» и «как» должны быть разделены и трассируемы — независимо от формы артефакта.

---

## 10. Резюме

| | SRS | SDD | ADR |
|---|---|---|---|
| **Вопрос** | Что? | Как? | Почему? |
| **Авторы** | Аналитик | Архитектор | Любой инженер |
| **Изменчивость** | Низкая | Средняя | Кумулятивная |
| **Главная ценность** | Единое понимание задачи | Руководство для реализации | История решений |

Все три артефакта образуют **триаду трассируемости**, без которой невозможно управление сложным проектом.
