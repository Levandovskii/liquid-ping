# Трассируемость требований

> Справочный материал курса «Жизненный цикл разработки ПО».
> Описывает принципы, виды, инструменты и метрики трассируемости — ключевого механизма управления требованиями.

## 1. Что такое трассируемость

**Трассируемость** — это способность проследить путь требования от источника (бизнес-цели) до проверки (тест-кейса) и обратно.

> **ISO/IEC/IEEE 15289:** *Происхождение каждого компонента может быть определено.*
> **ISO/IEC/IEEE 12207:** *Управление конфигурацией требует трассируемости элементов.*

### Зачем нужна трассируемость

| Задача | Что даёт трассируемость |
|--------|-------------------------|
| Обоснование требований | Доказать, что каждое требование имеет бизнес-цель |
| Оценка влияния изменений | Определить, какие артефакты затронет изменение |
| Контроль полноты реализации | Найти требования без кода и код без требований |
| Управление тестированием | Проверить, что каждое требование покрыто тестом |
| Аудит и сертификация | Подтвердить соответствие стандартам (DO-178C, IEC 62304) |

---

## 2. Виды трассируемости

| Вид | Направление | Вопрос |
|-----|-------------|--------|
| **Forward from source** | Источник → требование | Какие требования вытекают из бизнес-цели? |
| **Backward to source** | Требование → источник | Зачем нужно данное требование? |
| **Forward from requirements** | Требование → код/тесты | Где реализовано и как проверено? |
| **Backward to requirements** | Код/тесты → требование | Какое требование реализует данный код? |

### Полная цепочка

```text
Бизнес-цель
│ forward from source
▼
Пользовательское требование
│ forward from source
▼
Системное требование
│ forward from requirements
▼
Компонент дизайна
│ forward from requirements
▼
Модуль / класс
│ forward from requirements
▼
Строка кода
│ forward from requirements
▼
Тестовый сценарий
```

## 3. Типы связей

| Тип связи | Семантика | Пример |
|-----------|-----------|--------|
| **Satisfies** | Требование нижнего уровня удовлетворяет верхнему | FR-042 satisfies BR-01 |
| **Verifies** | Тест верифицирует требование | TC-012 verifies FR-042 |
| **Decomposes** | Требование декомпозируется на подтребования | FR-042 decomposes to FR-042.1, FR-042.2 |
| **Derives from** | Требование вытекает из другого | FR-042 derives from UC-003 |
| **Conflicts with** | Требования конфликтуют | FR-042 conflicts with FR-051 |
| **Traces to** | Общая связь трассируемости | DD-001 traces to FR-042 |

---

## 4. Матрица трассируемости

**Матрица трассируемости** — основной инструмент, в котором по строкам указаны требования, а по столбцам — артефакты.

### Пример фрагмента

| Req ID | Требование | UC | Дизайн | Код | Тест |
|--------|-----------|----|--------|-----|------|
| BR-01 | Безопасный доступ к счетам | UC-001 | DD-001 | Auth.java | TC-012 |
| FR-042 | Авторизация пользователя | UC-002 | DD-002 | AuthService.java | TC-013, TC-014 |
| FR-043 | Управление сессиями | UC-002 | DD-002 | SessionManager.java | TC-015 |
| NFR-008 | Шифрование TLS 1.3 | — | DD-010 | nginx.conf | TC-101 |

### Чтение матрицы

- **Пустые ячейки** — потенциальный пробел (требование не покрыто тестом или не реализовано).
- **«Подозрительные связи»** — связи, которые нужно пересмотреть после изменения требования.

---

## 5. Уровни детализации

| Уровень | Пример связи | Применение |
|---------|-------------|------------|
| **Грубый** | Пакет требований → модуль | Ранние этапы |
| **Средний** | Требование → компонент | Детальное проектирование |
| **Тонкий** | Требование → метод | Разработка, unit-тесты |
| **Максимальный** | Требование → строка кода | Сертификация (DO-178C, IEC 62304) |

**Правило:** Уровень детализации выбирается в зависимости от критичности проекта. Максимальная детализация — только для safety-critical систем.

## 6. Инструменты трассируемости

### 6.1 Ручные (таблицы, wiki)

**Когда применять:** до 100 требований, малые команды.

**Плюсы:** Дешевизна, быстрый старт.
**Минусы:** Не масштабируются, матрица устаревает.

### 6.2 Atlassian Jira + Xray / Zephyr

**Когда применять:** 100–1000 требований, Agile-команды.

**Возможности:**
- Иерархия Epic → Story → Task (вертикальная трассируемость)
- Связи: `blocks`, `relates to`, `tests`, `is tested by`
- JQL-запросы: `issue in linkedIssues("FR-042")`
- Плагины Zephyr и Xray связывают требования с тестами

**Ограничения:**
- Трассируемость через плагины
- Отсутствие автоматических «подозрительных связей»

### 6.3 IBM DOORS

**Когда применять:** тысячи требований, регулируемые отрасли.

**Возможности:**
- Сквозная прослеживаемость
- Базовые линии и контроль версий
- Link-модули с типами связей (satisfies, verifies, decomposes, derives from, conflicts with)
- Подозрительные связи (подсвечиваются при изменении)
- Стандарт обмена ReqIF

**Применение:** Авиация (DO-178C), автомобилестроение (ISO 26262), медицина (IEC 62304), оборонка.

### 6.4 Siemens Polarion

**Когда применять:** Enterprise-проекты, распределённые команды.

**Возможности:**
- Веб-платформа ALM
- Электронные подписи
- Workflow согласования
- Поддержка всех отраслевых стандартов

### 6.5 Docs-as-Code: Git + Markdown

**Когда применять:** Зрелые инженерные команды.

**Структура:**

```text
docs/
├── srs.md
├── requirements/
│   ├── REQ-FUNC-001.md
│   └── REQ-SEC-002.md
├── design/
│   └── auth-service.md
└── decisions/
    └── 0007-use-jwt.md
```

**CI-проверки:**
- Уникальность идентификаторов
- Полнота атрибутов
- Целостность ссылок матрицы
- Автосборка SRS при каждом изменении

**Плюсы:** История, ветвление, бесплатность, интеграция с CI/CD.
**Минусы:** Требует высокой дисциплины команды.

## 7. Метрики трассируемости

| Метрика | Целевое значение | Смысл |
|---------|-----------------|-------|
| **Покрытие трассируемостью** | ≥ 95% | Процент требований со связями |
| **Доля требований без источника** | 0% | Каждое требование имеет бизнес-обоснование |
| **Доля требований без тестов** | 0% | Полное покрытие тестами |
| **Доля закрытых подозрительных связей** | 100% за спринт | Изменения не остаются без анализа |
| **Среднее число связей на требование** | 3–7 | Нормальная связанность |

## 8. Трассируемость в регулируемых отраслях

| Отрасль | Стандарт | Требование |
|---------|---------|-----------|
| Авиация | DO-178C | Полная трассируемость до строки кода |
| Медицина | IEC 62304 | Требование → дизайн → код → тест |
| Автопром | ISO 26262 | Трассируемость safety-требований |
| Ж/д транспорт | EN 50128 | Полная трассируемость для SIL 3–4 |
| Финансы | PCI DSS, 152-ФЗ | Трассируемость требований безопасности |
| Атомная энергетика | IEC 61513 | Полная трассируемость safety-требований |

**Последствия отсутствия:** Отказ в сертификации, запрет на эксплуатацию, юридическая ответственность.

## 9. Практика: Requirements as Code

Современный подход к трассируемости — хранить требования как код:

```yaml
# requirements/REQ-FUNC-042.yaml
id: REQ-FUNC-042
title: Авторизация пользователя
statement: Система должна авторизовывать пользователя по логину и паролю
source: BR-01
priority: Must
status: Verified
links:
  - type: derives_from
    target: UC-002
  - type: satisfied_by
    target: DD-002
  - type: verified_by
    target: TC-013
version: 2.1
```

**Преимущества:**
- Автоматическая генерация матрицы трассируемости
- CI-проверки целостности связей
- Интеграция с Git-историей
- Ветвление требований вместе с кодом

## 10. Антипаттерны

| Проблема | Последствия | Решение |
|----------|-------------|---------|
| Трассируемость не ведётся | Невозможность оценить влияние изменений | Включить в Definition of Done |
| Матрица устаревает | Ложная уверенность в полноте | Автоматизация через RM-систему |
| Избыточная детализация | Дорогое сопровождение | Адекватный уровень гранулярности |
| Разрывы цепочек | Скрытые риски | Регулярный аудит трассируемости |
| Сопротивление команды | Саботаж процесса | Обучение, демонстрация ценности |

## 11. Аудит трассируемости

### Периодичность

- Перед базовой линией
- Перед релизом
- При смене владельца проекта

### Контрольный список

- ✅ Все требования имеют уникальный ID и актуальный статус
- ✅ Отсутствуют требования без источника
- ✅ Матрица трассируемости заполнена
- ✅ Все изменения оформлены запросами
- ✅ Подозрительные связи пересмотрены
- ✅ Покрытие тестами ≥ 95%

---

## 12. Резюме

Трассируемость — это кровеносная система проекта. Без неё:

- Изменения превращаются в «стрельбу по площадям»
- Тестирование теряет полноту
- Сертификация невозможна
- Команда теряет контроль над проектом

**Золотое правило:** Каждое требование имеет источник, реализацию и проверку. Связи между ними зафиксированы.
