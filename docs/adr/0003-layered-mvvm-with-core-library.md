# ADR-0003: Архитектура — два проекта (Core и App), MVVM и внедрение зависимостей

## Контекст и постановка задачи

SRS требует отделить слой интерфейса от сетевой логики, тестировать логику без UI и оформить её отдельной библиотекой без зависимостей от WPF (SRS 3.5.4, 3.5.5). Приложение небольшое, разрабатывается одним человеком.

Вопрос: как организовать код, чтобы выполнить эти требования, не усложняя проект сверх меры?

## Драйверы решения

* Тестируемость сетевой логики без запуска интерфейса (SRS 3.5.4)
* Независимость логики от WPF (SRS 3.5.5)
* Простота и соразмерность масштабу проекта
* Возможность подменять реализации (проверки, хранилище) в тестах

## Рассмотренные варианты

* Один проект, логика в code-behind
* Два проекта (`LiquidPing.Core` и `LiquidPing.App`), MVVM и внедрение зависимостей
* Многослойная чистая архитектура из четырёх и более проектов

## Итог решения

Выбранный вариант: «Два проекта, MVVM и внедрение зависимостей», потому что он напрямую выполняет требования SRS 3.5.4 и 3.5.5 при минимальной сложности. Для MVVM используется библиотека CommunityToolkit.Mvvm, для внедрения зависимостей — Microsoft.Extensions.DependencyInjection (обе под лицензией MIT).

### Последствия

* Хорошо, потому что `Core` тестируется модульными тестами без интерфейса.
* Хорошо, потому что `Core` можно переиспользовать, например, в консольной утилите.
* Хорошо, потому что разделение остаётся простым и понятным для сопровождающих.
* Плохо, потому что появляются два сторонних пакета и необходимость поддерживать корень композиции.
* Плохо, потому что для маленького приложения MVVM добавляет шаблонный код.

### Подтверждение

Автоматический тест проверяет, что сборка `LiquidPing.Core` не ссылается на сборки WPF (`PresentationFramework`, `PresentationCore`, `WindowsBase`). Code review проверяет, что ViewModel не содержат ссылок на элементы управления.

## Плюсы и минусы вариантов

### Один проект, логика в code-behind

* Хорошо, потому что самый быстрый старт.
* Плохо, потому что нарушает SRS 3.5.4 и 3.5.5.
* Плохо, потому что логику сложно тестировать.

### Два проекта, MVVM и внедрение зависимостей

* Хорошо, потому что выполняет требования SRS и остаётся простым.
* Хорошо, потому что проверки и хранилища подменяются в тестах.
* Нейтрально, потому что требуется освоить корень композиции.
* Плохо, потому что немного шаблонного кода.

### Многослойная чистая архитектура

* Хорошо, потому что строгие границы слоёв.
* Плохо, потому что избыточно для приложения такого размера.
* Плохо, потому что замедляет разработку и увеличивает объём документации.

## Дополнительная информация

Связанные требования: SRS 3.5.4, 3.5.5, REQ-COMP-001. Представления SDD: 002-composition, 011-patterns, 013-dependency. Решение пересматривается, если появятся новые клиенты `Core` (например, консольный интерфейс).
