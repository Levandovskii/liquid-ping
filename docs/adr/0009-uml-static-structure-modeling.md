# ADR-0009: Моделирование статической структуры на UML

## Контекст и постановка задачи

В ADR-0008 выбрана нотация PlantUML и построена модель динамического поведения: варианты использования, активности, состояния и последовательности. Для полного описания дизайна не хватает статической структуры: какие классы существуют, из каких компонентов состоит сборка и на каких узлах работает приложение. Без этих диаграмм нельзя проверить, что проект 003-logical SDD реализуем, что границы проектов `LiquidPing.App` и `LiquidPing.Core` соблюдены и что требования к поставке и платформе (SRS 3.5) отражены в дизайне.

Дополнительная сложность: классы проектируются до написания кода, поэтому диаграммы должны одновременно соответствовать контрактам SDD 005, принятым решениям ADR-0003…ADR-0007 и будущей структуре проектов, чтобы при реализации не пришлось переписывать модель.

Вопрос: какими диаграммами описывать статическую структуру, как разбить их на читаемые части и как связать между собой, с требованиями и с кодом?

## Драйверы решения

* Полнота: классы, компоненты и развёртывание — три обязательных представления статической структуры
* Читаемость: диаграмма должна читаться на странице отчёта, поэтому одна большая диаграмма классов недопустима
* Соответствие контрактам SDD 005 и правилу зависимостей `App → Core` (ADR-0003)
* Текстовый формат, пригодный для git и code review, без платных инструментов
* Прослеживаемость: каждая диаграмма связана с требованиями `REQ`, системными требованиями `SYS` и представлениями SDD

## Рассмотренные варианты

* PlantUML: обзорная и пять детальных диаграмм классов, диаграмма компонентов и диаграмма развёртывания
* Mermaid: `classDiagram` и схема развёртывания
* Графический редактор (draw.io или Visio)
* Автоматическая генерация диаграмм из кода (reverse engineering)

## Итог решения

Выбранный вариант: «PlantUML», потому что он уже принят в ADR-0008, поддерживает все три типа диаграмм в стандартной нотации UML и остаётся текстом. Модель статической структуры состоит из восьми диаграмм:

| Файл                      | Тип          | Содержание                                              |
|---------------------------|--------------|---------------------------------------------------------|
| `class-overview.puml`     | классов      | обзор всех ключевых типов и связей проекта              |
| `class-monitoring.puml`   | классов      | модели, проверки, мониторинг и оценка статуса           |
| `class-network.puml`      | классов      | сканирование портов и обнаружение хостов                |
| `class-storage.puml`      | классов      | хранение данных и вспомогательные сервисы               |
| `class-viewmodels.puml`   | классов      | слой представления MVVM                                 |
| `class-services.puml`     | классов      | сервисы оболочки приложения                             |
| `component-overview.puml` | компонентов  | проекты сборки, контракты и внешние компоненты          |
| `deployment-overview.puml`| развёртывания| узлы, среда исполнения, артефакты и протоколы связи     |

Исходники лежат в `docs/uml/src`, PNG с теми же именами — в `docs/uml/img`; в SDD на PNG даются ссылки, рядом указывается исходник. Схема состава в Mermaid, которая была в SDD до версии 0.4, заменена диаграммой компонентов UML: два формата для одной сущности не нужны.

### Механизм построения диаграмм классов

Диаграммы классов строятся от данных к сервисам и далее к представлению:

1. **Типы данных** (`Host`, `ProbeResult`, `HostSnapshot`, `AppSettings`, перечисления) выводятся из представления 004-information и таблицы 003-logical.
   Обзорная диаграмма собирает ключевые типы всех пакетов и служит оглавлением модели, а детальные диаграммы раскрывают каждый пакет.
2. **Сервисы ядра** добавляются по контрактам SDD 005: для каждого интерфейса (`IProbe`, `IMonitoringService`, `IPortScanner`, `ILanDiscovery`, `IOuiLookup`, `IHostRepository`, `ISettingsStore`) на диаграмме есть реализация и отношение реализации.
3. **Модели представления** получают зависимости только от контрактов ядра, что фиксирует правило `App → Core`.
4. **Разбиение по пакетам** выполнено по пространствам имён `LiquidPing.Core.*` и `LiquidPing.App.*`. В одной диаграмме не больше двадцати классов: иначе текст становится нечитаемым при печати. Диаграммы связаны общими типами: `Host` и `HostSnapshot` встречаются в нескольких диаграммах как ссылки, а полное описание получают в своей.

На диаграммах используются следующие обозначения:

| Обозначение | Смысл в модели                                                             |
|-------------|----------------------------------------------------------------------------|
| `+`, `-`, `#` | видимость `public`, `private`, `protected`                               |
| `-->`       | однонаправленная ассоциация                                                |
| `o-->`      | агрегация: часть может существовать отдельно (набор проверок у сервиса)    |
| `*-->`      | композиция: часть создаётся и уничтожается владельцем (окна результатов)   |
| `..>`       | зависимость: использование без хранения ссылки                             |
| `..|>`      | реализация интерфейса                                                      |
| `--|>`      | наследование класса                                                        |

## Механизм построения диаграммы компонентов

Диаграмма компонентов выводится из структуры решения, а не из классов:

1. **Компонент** — единица сборки или крупная часть приложения: `LiquidPing.App`, `LiquidPing.Core`, `LiquidPing.Core.Tests`. Внутри `App` показаны Views, ViewModels и оболочка, внутри `Core` — шесть подсистем, совпадающих с пакетами диаграмм классов.
2. **Точки соединения** — контракты SDD 005. Стрелка от потребителя к поставщику подписана словом «контракты», а полный перечень интерфейсов приведён в SDD 005; поэтому видно, что приложение зависит от интерфейсов, а не от реализаций.
3. **Внешние компоненты** — подсистемы Windows: сетевой стек (Winsock, DNS, IP Helper API), DWM, центр уведомлений, файловая система. Они вынесены в пакет «Среда исполнения» и соединены с теми подсистемами, которые к ним обращаются.
4. **Направление зависимостей** совпадает с ADR-0003: `App` зависит от `Core`, тесты — от `Core`, обратных стрелок нет.

## Механизм построения диаграммы развёртывания

Диаграмма развёртывания выводится из требований к платформе и поставке (SRS 2.3, 3.5.1, 3.5.2; ADR-0007):

1. **Узел** `<<device>>` — рабочая станция пользователя под Windows 11 x64; отдельными узлами показаны коммутатор локальной сети, хосты локальной сети, DNS-сервер и узлы интернета.
2. **Среда исполнения** `<<execution environment>>` — .NET 10 в режиме self-contained; внутри неё размещены артефакты `LiquidPing.App.exe`, `LiquidPing.Core.dll` и сторонние библиотеки.
3. **Артефакт** соответствует компоненту: `LiquidPing.App.exe` собран из компонента `LiquidPing.App`, `LiquidPing.Core.dll` — из `LiquidPing.Core`; связь артефактов показывает вызов контрактов.
4. **Хранилище данных** — узел данных `%AppData%\LiquidPing` с файлами `hosts.json`, `settings.json` и журналом.
5. **Линии связи** подписаны протоколами: Ethernet или Wi-Fi 802.11, IPv4/ICMP/ARP, ICMP/TCP/HTTP(S), DNS. Это показывает, что других каналов, кроме сети и файловой системы, у приложения нет.

### Связи между диаграммами и трассируемость

| Диаграммы классов                | Компонент (002)              | Артефакт (012)                  | Требования SRS / SYS                              |
|----------------------------------|------------------------------|---------------------------------|---------------------------------------------------|
| `class-monitoring`               | Monitoring, Probes           | `LiquidPing.Core.dll`           | REQ-FUNC-003…009, 016; SYS-FUNC-002, 003, 004     |
| `class-network`                  | Scanning, Discovery          | `LiquidPing.Core.dll`           | REQ-FUNC-010…012, 020…022; SYS-FUNC-005, 006, 015, 016 |
| `class-storage`                  | Storage, Support             | `LiquidPing.Core.dll`, AppData  | REQ-FUNC-001, 002, 014, 015, 017, 018; REQ-REL-002; SYS-FUNC-001, 008, 010, 011, 013 |
| `class-viewmodels`, `class-services` | App: Views, ViewModels, Оболочка | `LiquidPing.App.exe`      | REQ-FUNC-013, 019; REQ-INT-002, 008; SYS-FUNC-007, 009, 012, 014 |
| `component-overview`             | все компоненты               | оба артефакта                   | ADR-0003, SYS-NFR-011                             |
| `deployment-overview`            | все компоненты               | переносимый архив `win-x64`     | REQ-COMP-001, REQ-SEC-001; ADR-0007               |

Цепочка трассируемости: требование `REQ` → системное требование `SYS` (SDD 5.2) → класс или подсистема на диаграмме классов → компонент и артефакт → узел развёртывания. Имена классов, интерфейсов и компонентов на диаграммах совпадают с идентификаторами C# и именами проектов, поэтому трассируемость проверяется по коду.

### Правила сопровождения

* Изменение контракта или состава классов сопровождается правкой соответствующего `.puml` и повторным экспортом PNG в том же коммите.
* Новая подсистема добавляется на диаграмму компонентов и в одну из диаграмм классов, а не в общую схему.
* На code review проверяется, что число классов на диаграмме не превышает 15 и что PNG соответствует исходнику.
* Диаграммы не дублируют код дословно: на них выводятся значимые члены, а полный набор методов определяется реализацией и тестами.

## Последствия

* Хорошо, потому что статическая структура описана в той же нотации, что и динамическая, и хранится в git как текст.
* Хорошо, потому что разбиение по пакетам делает каждую диаграмму читаемой и позволяет обновлять только затронутую часть модели.
* Хорошо, потому что диаграмма компонентов фиксирует правило `App → Core`, а диаграмма развёртывания — отсутствие внешних сервисов.
* Нейтрально, потому что для сборки PNG нужен PlantUML или сервис Kroki, которого нет в стандартной поставке .NET.
* Плохо, потому что семь диаграмм нужно синхронизировать с кодом при каждом изменении контрактов.
* Плохо, потому что схема состава в Mermaid, которую GitHub рисовал сам, заменена на PNG и больше не отображается без экспорта.

## Подтверждение

Каждый `.puml` рендерится без ошибок, для него в `docs/uml/img` есть актуальный PNG (проверка на code review). Имена классов и интерфейсов на диаграммах совпадают с кодом проектов `LiquidPing.Core` и `LiquidPing.App`, а идентификаторы `REQ` и `SYS` — с SRS и SDD 5.2. Правило зависимостей проверяется по графу ссылок проектов: у `LiquidPing.Core` нет ссылки на WPF.

## Плюсы и минусы вариантов

### PlantUML

* Хорошо, потому что поддерживает диаграммы классов, компонентов и развёртывания в нотации UML и уже используется в проекте.
* Хорошо, потому что исходник — текст, пригодный для diff и code review.
* Нейтрально, потому что PNG нужно экспортировать отдельным шагом.
* Плохо, потому что автоматическая раскладка больших диаграмм требует ручного разбиения на части.

### Mermaid

* Хорошо, потому что GitHub рисует диаграммы без экспорта.
* Плохо, потому что `classDiagram` не поддерживает все нужные элементы (например, полный набор отношений композиции с кратностями), а диаграмма развёртывания выражается условно.
* Плохо, потому что получилось бы два формата: динамика в PlantUML, статика в Mermaid.

### Графический редактор

* Хорошо, потому что полная свобода компоновки.
* Плохо, потому что бинарные файлы плохо сравниваются в git.
* Плохо, потому что ручная компоновка расходится с кодом при изменении контрактов.

### Генерация из кода

* Хорошо, потому что диаграмма всегда соответствует коду.
* Плохо, потому что на момент проектирования кода ещё нет, а сгенерированная диаграмма содержит служебные типы и плохо читается.
