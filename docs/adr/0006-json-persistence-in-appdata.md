# ADR-0006: Хранение данных — JSON-файлы в AppData, история только в памяти

## Контекст и постановка задачи

Приложение должно сохранять список узлов и настройки между запусками (REQ-FUNC-002, 017), восстанавливаться после повреждения файлов (REQ-REL-002) и вести журнал (REQ-OBS-001). Хранение истории проверок между сеансами в версию 1.0 не входит (SRS 1.2). Телеметрии и облачных аккаунтов нет (REQ-SEC-003).

Вопрос: в каком формате и где хранить постоянные данные?

## Драйверы решения

* Простота и отсутствие дополнительных зависимостей
* Читаемость и возможность ручной правки
* Устойчивость к повреждению и сбоям записи (REQ-REL-002)
* Небольшой объём данных
* Отсутствие необходимости в запросах и истории между сеансами

## Рассмотренные варианты

* JSON-файлы в `%AppData%\LiquidPing\` (`System.Text.Json`)
* SQLite
* Реестр Windows

## Итог решения

Выбранный вариант: «JSON-файлы в AppData», потому что объём данных мал, запросы не нужны, а формат читаем и не требует зависимостей. Запись выполняется через временный файл с последующей заменой; повреждённый файл переименовывается в `*.bak`, и применяются значения по умолчанию.

### Последствия

* Хорошо, потому что нет зависимостей и формат понятен человеку.
* Хорошо, потому что восстановление после повреждения реализуется просто.
* Плохо, потому что нет запросов и индексов; при появлении истории между сеансами формат придётся пересмотреть.
* Плохо, потому что нужна аккуратная атомарная запись и поле `version` для миграций формата.

### Подтверждение

Тест подмены файла некорректным содержимым: приложение запускается, исходный файл сохранён как `.bak` (REQ-REL-002). Тест изменения списка узлов и перезапуска (REQ-FUNC-002).

## Плюсы и минусы вариантов

### JSON-файлы в AppData

* Хорошо, потому что простота и читаемость.
* Хорошо, потому что нет зависимостей.
* Нейтрально, потому что требуется версионирование формата.
* Плохо, потому что нет запросов к истории.

### SQLite

* Хорошо, потому что транзакции и запросы.
* Плохо, потому что дополнительная зависимость и нативные библиотеки.
* Плохо, потому что избыточно для списка узлов и настроек.

### Реестр Windows

* Хорошо, потому что штатное место для настроек.
* Плохо, потому что неудобно переносить и править вручную.
* Плохо, потому что список узлов плохо ложится на структуру реестра.

## Дополнительная информация

Связанные требования: REQ-FUNC-001, 002, 017, REQ-REL-002, REQ-OBS-001, REQ-SEC-003. Представление SDD: 004-information. Решение пересматривается, если в SRS появится хранение истории между сеансами (тогда рассматривается SQLite).
