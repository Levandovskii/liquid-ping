# ADR-0008: Моделирование динамического поведения на UML средствами PlantUML

## Контекст и постановка задачи

Для проекта нужна модель динамического поведения: варианты использования, активности, состояния и взаимодействия компонентов. Модель должна быть связана с SRS и SDD, храниться в репозитории рядом с кодом и документами и изменяться вместе с ними. В SDD уже используются диаграммы Mermaid, но Mermaid не поддерживает полноценные диаграммы вариантов использования и активности с нотацией UML.

Вопрос: чем и как описывать UML-диаграммы, какой набор диаграмм использовать и как связать их между собой?

## Драйверы решения

* Поддержка четырёх типов UML: варианты использования, активности, состояния, последовательности
* Текстовое описание, которое можно версионировать в git и просматривать в diff
* Нотация, близкая к стандартной UML (ссылки `ref`, `create`/`destroy`, составные состояния, `include`/`extend`)
* Отсутствие платных инструментов и зависимостей в проекте
* Прослеживаемость диаграмм к требованиям SRS и элементам SDD

## Рассмотренные варианты

* PlantUML (диаграммы как код)
* Mermaid
* Графический редактор (draw.io или Visio)

## Итог решения

Выбранный вариант: «PlantUML», потому что он единственный из рассмотренных покрывает все четыре типа UML в стандартной нотации и при этом остаётся текстом, хранимым в git.

Исходники (`.puml`) лежат в `docs/uml/src`, экспортированные PNG — в `docs/uml/img` под тем же именем; в SDD на PNG даются ссылки, а исходник указывается рядом. Диаграмма состава приложения в SDD остаётся в Mermaid, так как GitHub рисует её без дополнительных шагов.

### Механизм построения и связи диаграмм

Диаграммы строятся последовательно, и каждая следующая уточняет предыдущую:

1. **Варианты использования** выводятся из требований SRS: каждый прецедент связан с одним или несколькими `REQ`, актёры — внешние лица и системы.
2. **Активность** детализирует поток событий одного прецедента: ветвления, циклы, ожидание действия пользователя.
3. **Состояния** описывают жизненный цикл ключевой сущности, которая появляется в потоках прецедентов (статус узла).
4. **Последовательность** показывает, какие компоненты SDD обмениваются сообщениями при выполнении прецедента, и связывает сценарий с проектными представлениями.

| Прецедент                         | Активность                         | Состояния              | Последовательность                 | Требования SRS / SYS                          |
|-----------------------------------|------------------------------------|------------------------|------------------------------------|-----------------------------------------------|
| UC-03 Выполнить цикл проверок     | —                                  | Статус узла            | Цикл мониторинга                   | REQ-FUNC-003…009; SYS-FUNC-002…004            |
| UC-06 Обнаружить хосты в сети     | Обнаружение хостов в сети          | —                      | —                                  | REQ-FUNC-020, 021; SYS-FUNC-006, 015          |
| UC-07 Добавить найденный хост     | Обнаружение хостов в сети (конец)  | —                      | —                                  | REQ-FUNC-022; SYS-FUNC-016                    |
| UC-02 Запустить и остановить      | —                                  | Статус узла (Stopped)  | Цикл мониторинга (Start, Stop)     | REQ-FUNC-008; SYS-FUNC-004                    |

Для каждого прецедента в `docs/uml/use-cases.md` приведены пояснение, предусловия, потоки событий и постусловия; идентификаторы `UC-NN`, `REQ-…` и `SYS-…` образуют цепочку трассируемости от требования до сценария.

### Последствия

* Хорошо, потому что диаграммы версионируются и сравниваются как текст.
* Хорошо, потому что нотация близка к стандартной UML и совпадает с заданием.
* Хорошо, потому что цепочка прецедент → активность → состояния → последовательность делает модель проверяемой на согласованность.
* Плохо, потому что для получения PNG нужен инструмент (плагин или сервис PlantUML), а GitHub не рисует PlantUML сам.
* Плохо, потому что в SDD теперь два формата диаграмм (PlantUML и Mermaid).
* Плохо, потому что PNG нужно экспортировать заново при каждой правке исходника.

### Подтверждение

Каждый `.puml` рендерится без ошибок, а для него в `docs/uml/img` есть актуальный PNG (проверка на code review перед слиянием). Идентификаторы `UC`, `REQ` и `SYS` на диаграммах совпадают с `docs/uml/use-cases.md` и SDD 5.2.

## Плюсы и минусы вариантов

### PlantUML

* Хорошо, потому что поддерживает все нужные типы диаграмм и нотацию UML.
* Хорошо, потому что текстовый формат подходит для git.
* Нейтрально, потому что требуется Java или онлайн-сервис для рендеринга.
* Плохо, потому что GitHub не отображает его без экспорта.

### Mermaid

* Хорошо, потому что GitHub рисует диаграммы без дополнительных шагов.
* Плохо, потому что нет диаграммы вариантов использования; активность выражается через блок-схему, а не нотацией UML.
* Плохо, потому что ограниченная поддержка элементов диаграммы последовательности (например, `ref`, создание и уничтожение участника).

### Графический редактор (draw.io или Visio)

* Хорошо, потому что полная свобода рисования.
* Плохо, потому что бинарные или объёмные файлы плохо сравниваются в git.
* Плохо, потому что правки вручную трудно согласовывать с требованиями.
